# Day 14：Gameplay Framework 周整合与职责边界

## 背景与目标

### 背景

`Week 2` 前几天分别验证了 `World`、`Subsystem`、`GameMode`、`GameState`、`PlayerController`、`PlayerState`、`Pawn`、`Possess`和重生，单独验证每个机制，还不能证明这些对象之间的职责没有混乱。所以需要整合一下 `Week2` 的内容，另外，当前项目还缺少自动测试的机制，需要建立自动测试的机制。

### 目标

- 画一张 `Week 2` 涉及的所有对象的实例图；通过 `Functional Test` 验证 `Spawn`、`Possess`、返回原 `Character` 和清理。
- 对原始 `Lvl_ThirdPerson` 进行 `Smoke` 验证，确保 `Week 2` 新增功能没有破坏原有移动、跳跃和相机。
- 通过全新 `Clone` 回归证明工程可以从远端恢复、重新构建和重新运行。

## 关键概念

| 对象 | 职责 | 数据或行为边界 |
|---|---|---|
| `GameMode` | 服务器权威规则、登录、重生和流程决策 | 不作为客户端共享数据来源 |
| `GameState` | 整局或当前关卡的共享状态 | 服务器写入，客户端通过复制观察 |
| `PlayerController` | 输入入口、Server RPC、Possess 和本地 UI 协调 | 代表玩家的控制通道 |
| `PlayerState` | 玩家身份、分数、队伍等状态 | 相对 Pawn 保持更长生命周期并可复制 |
| `Pawn/Character` | 世界中的身体、移动、碰撞和身体能力 | 可以死亡、销毁、替换和重生 |
| `UAegisSessionSubsystem` | 跨 World 的本地服务 | 依附 `GameInstance` |
| `UAegisLocalSettingsSubsystem` | 单个本地玩家的设置 | 依附 `ULocalPlayer` |

- `GameState` 是服务器上每个运行时 `World` 的实例，不是每个玩家一份。
- 普通客户端通常只有自己的 `PlayerController`，但可以通过复制得到其他玩家的 `PlayerState`。
- `PlayerState` 的“持久”是相对于 `Pawn` 生命周期而言，不代表跨断线或跨进程永久保存。
- `UAegisSessionSubsystem` 继承自 `GameInstanceSubsystem`，其 `Outer` 是 `GameInstance`，`UAegisLocalSettingsSubsystem` 继承自 `ULocalPlayerSubsystem`，其 `Outer` 是 `LocalPlayer`。
- `GameMode`、`GameState`、`PlayerController` 和 `PlayerState` 不能因为都属于 `Gameplay Framework` 就混用职责。

### Gameplay Framework 实例图

- 这是运行实例图，不是项目类图，展示服务器/客户端的典型运行时对象关系。
- 左边是服务器 `World`，在服务器 `World` 上有 `GameMode`、`GameState`、`PlayerController`、`PlayerState`、`Character`、`ObserverPawn`（`Tab`切换的时候用到）、`FT_SpawnPossess`（自动测试用到）。
- 右边是某个拥有者客户端 `World`；在客户端 `World` 上有 `GameState`、`PlayerController`、`PlayerState`、`Character`。普通客户端通常只拥有自己的 `PlayerController`，但可以通过复制观察其他玩家的 `PlayerState`。
- `UAegisSessionSubsystem` 的 `Outer` 是 `GameInstance`，`UAegisSessionSubsystem` 能跨 `World` 存在；而 `LocalSettingSubsystem` 的 `Outer` 是 `LocalPlayer`，一个 `LocalPlayer` 对应一个 `ULocalPlayerSubsystem`。

### Functional Test

- `AFunctionalTest` 是 `Unreal Engine` 提供的功能测试 `Actor`，用来在真实关卡和 `Gameplay World` 中自动执行一段场景验证，并明确给出成功或失败结果，它特别适合验证依赖 `Actor`、`World`、组件和 `Gameplay Framework`。比如： `Actor` 能否成功 `Spawn`、`Controller` 能否正确 `Possess Pawn`、触发机关后门是否打开、`AI` 是否能到达目标、重生后是否生成了正确 `Pawn`、多个 `Actor` 之间的运行时关系是否符合预期。
- 为了自动测试，新建了测试模块 `ProjectAegisTests`，测试模块依赖 `FunctionalTesting`、`Engine`、`Core` 和 `CoreUObject`。`ProjectAegisTests` 不依赖 `ProjectAegis Runtime` 模块。
- 在测试时是使用 `APlayerController`、`APawn` 和可配置的 `TSubclassOf<APawn>`。因为这样可以减少 `DLL` 的公共导出面，也避免测试代码与 `Runtime` 实现形成不必要的耦合。另外，`Functional Test` 属于开发测试能力，不应把 `FunctionalTesting` 依赖和测试逻辑带入正式 `Runtime` 或 `Shipping` 边界。

## 我的理解

这一周主要学习和验证了 `Gameplay Framework` 中主要的概念以及对应的原理，比如 `GameMode` 用来做服务器权威的规则、流程和决策，`PlayerState` 不会随着 `Character` 的销毁而销毁，所以常常用来保存一局游戏的玩家的一些信息，比如玩家所属队伍和分数；一局游戏可能出现跨 `World` 的情况，所以跨 `World` 的服务放到 `UGameInstanceSubsystem`，一个玩家的本地设置放在 `ULocalPlayerSubsystem`，因为 `ULocalPlayerSubsystem` 的 `Outer` 是 `LocalPlayer`。另外，这周建立工程的自动化测试模块 `ProjectAegisTests`，普通日志实验只能证明某一次人工操作发生了什么，`AFunctionalTest` 是放在正式 `World` 中运行的测试 `Actor`，可以对 `Spawn`、`Possess`、`Actor` 生命周期等世界行为给出机器可判断的成功或失败。`Functional Test` 属于开发测试能力，不应该把 `FunctionalTesting` 依赖和测试逻辑带入正式 `Runtime` 或 `Shipping` 边界，所以建立独立的 `ProjectAegisTests DeveloperTool` 模块。
